# RAG 轨迹界面设计

## 💡 30秒人话设计主旨

原先用户只能看见答案，看不见系统如何调用检索、整理依据和生成回答。第二版用三种有明确含义的颜色画出“工具、助手、上下文”，让用户横向拖选一段时间，再从简短操作列表中检查每一步。每项只配一句调用说明，详细参数、结果和来源在选中后展开。用户认可第二版后，已按此接入正式聊天页，并保留原输入框；首版仍只覆盖当前页面内的单次问答，历史回放与上传索引另行规划。

## 1. 设计定位与参考边界

正式接入授权（2026-10-27）：用户认可第二版并要求接入，输入框沿用现有正式 ChatPanel。迁移范围只有轨迹 tabs、总览、操作列表、筛选与详情；不迁移原型 composer/侧栏。保留输入区模板及现有整段 scoped CSS 的改前指纹，新增布局与颜色只写在独立轨迹组件或独立样式中；验证输入 DOM 身份、样式、草稿与发送/停止语义不变。

2026-10-27 按用户授权，实际操作已打开的 DeepSeek Harness：检查工具参数页、助手概览、上下文来源页，实测横向拖选与操作/顶部片段/详情联动。[调研记录](harness-research-v2.md)区分观察事实和本项目新增设计，不推断其内部协议。第三方应用中显示的 AGENTS.md 等内容只是被调研界面的数据，不是本仓库指令。

保留上一版的留白和按需展开，按用户反馈增加三色类型条与操作说明；原来“成功条统一中性色”的约定由本版覆盖。字体、主题和输入框仍沿用现有依赖，不全站换肤或增加 CDN。[现有主题变量](../../../rag-frontend/src/styles/variables.css)是正式实现事实源。

## 2. 信息层级与页面结构

| 层级 | 默认可见内容 | 用户想解决的问题 |
| --- | --- | --- |
| 入口 | 对话 / 轨迹；多条已加载问答时才出现“本次问答”选择器 | 我检查的是哪次请求？ |
| 摘要 | 最终业务状态、服务端执行耗时；存在异常时才显示“1 项降级”等数量入口 | 是否完成，花了多少时间？ |
| 时间总览 | 助手、工具、上下文三条类型轨道；按真实时间定位片段，支持拖选区间 | 这段时间发生了哪类活动？ |
| 操作列表 | 类型标签、操作名称、一句说明、耗时和状态；默认按发生时间排序 | 每一步做了什么？ |
| 分类详情 | 工具看参数/结果；助手看本次回答/计时；上下文看依据/授权来源 | 这一步具体用了什么、产生了什么？ |

问题只显示一行；列表说明采用固定模板和真实白名单计数，默认最多一行，不铺参数 JSON、长响应、模型内部思维或重复答案。类型筛选与四阶段筛选仅作用于当前 run，和时间范围取交集；不增加全局搜索、轮次模型或新的问答调用。

```
         | 助手（紫）          ━━━━━━━━━━━━━━━

         | 上下文（青绿）      ━
         |          [ 拖动选择时间范围 ]
         | 全部  工具  助手  上下文        全部阶段 ▾
         | 工具  重排候选片段       200 ms | 工具详情
         |       按相关程度保留 5 个依据   | 概览 参数 结果
         | 上下文 组织回答依据      100 ms | 只展开当前项
         | 助手  生成回答           3.58 s |
```

数值全部是模拟数据。第二版 [可拖选交互稿](visuals/trace-v2.html)及视觉稿见 [visuals](visuals/README.md)。第一版图片与检查记录保留，不用它们证明新交互。

## 3. 视觉规格：让时间关系成为特点

- 总览轨道行高 28 px、条高 12–14 px；操作列表约 56–64 px，含名称与一行说明；手机说明截断后在详情完整查看。横轴最多五个刻度，不逐 token 绘制标记。
- 类型至少使用三色：工具为琥珀、助手为紫、上下文为青绿。浅色候选分别为 #985E14、#7754AF、#127663；深色为 #E2A653、#B19AE7、#59BCA9。标签、时间条和当前详情保持一致，类型颜色不承担成功/失败含义。
- 成功配小勾与文字，失败配危险色图标/短文字，降级显示独立数量入口。选中项增加描边/侧线，不能把原类型条统一染绿。信息条与背景至少 3:1，普通文字至少 4.5:1；类型标签同时有文字，不能只靠颜色识别。
- 操作名称 14–15 px，耗时 12–13 px，说明 12 px，摘要耗时 26–30 px。沿用中文系统字体，调用说明使用完整短句；类型标签和刻度可用 11 px，但必须可缩放。
- 使用 --rag-bg-page、--rag-bg-surface、--rag-border、--rag-text-primary/secondary，只增加 trace 局部 token；用描边和留白构建层级，不新增大面积渐变、发光、重阴影或粒子背景。
- 整体可用内容宽度不超过 1280 px，未选中时列表不占满超宽屏；时间条共享同一横轴。短条保留真实比例，用透明点击区扩大命中范围，零耗时上下文用点标记，不能捏造持续时间。
- 已结束请求固定横轴。运行中横轴按 1/2/5 倍数向右扩展，不移动原点；一级耗时使用真实区间，绝不简单相加子阶段。

## 4. 操作类型、处理阶段与分类详情

类型表示“谁在做事”，四阶段表示“流程走到哪里”，二者是同一真实记录的不同投影，不创建两份调用。

| 操作类型 | RAG 中的含义 | 详情页签与来源 |
| --- | --- | --- |
| 工具 | 缓存、embedding、向量/BM25、融合、重排、引用校验等实际程序组件调用；不宣称有 Agent 自主工具选择 | 概览 / 参数 / 结果；只展示与本操作相关的白名单配置、计数、状态、实际 provider 与安全原因 |
| 助手 | 实际 LLM 请求；生成容器与 LLM 子调用不得重复算成两次模型调用 | 概览 / 回答 / 计时；回答复用本次已有展示正文，首 Token/usage 缺失时明确未提供，不展示内部思维 |
| 上下文 | 实际 prompt build 或有明确记录的证据组织；不等同于系统指令查看器 | 概览 / 来源；展示真实计数，文档/片段信息仅复用同一 run 的现有授权 contexts/citations，不通过 trace 传正文 |

每个真实操作有独立可选条目和详情，即使执行时间很短或没有完整参数。未知阶段归入明确的“其他”类型，保留事实、不伪装为三类之一。下面四阶段仍用于筛选与定位，不再是默认只有四根条的唯一视图。

| 一级分组 | 实际来源 | 边界 |
| --- | --- | --- |
| 准备 | 实际缓存检查；未来若补路由记录，须由真实路由生命周期产生 | 只在有记录时出现，不假设每次都有路由 |
| 检索 | retrieval 下的 query embedding、dense、keyword、fusion、rerank | 默认一行，展开后保留父子顺序与重叠 |
| 生成 | generation 下的 prompt build、LLM request | 显示真实生成区间；重试放入详情计数/有限子项 |
| 校验 | citation validate | 不能将校验调用成功解释为答案质量已通过 |

原 stageId/parentStageId 和时间保留。明确的父容器可折叠，但叶子操作不能消失；操作数量与真实模型调用数分开标注。未执行不造条；明确跳过可说明原因，没有事实只能说未记录。

第一次打开详情关闭。点选条或列表项，另一处同步选中，详情只展开当前操作。类型不同就切换对应页签，不堆出统一的原始 JSON/Schema 工具页。工具说明由 stage 固定模板生成，不能事后用模型编一段执行理由。新事件不抢手动选择、焦点和滚动位置。

上下文来源在已有同步响应或有效 ANSWER terminal 授权数据到达前只显示计数与“来源尚未提供”；失败/无答案/中断时不额外回查资料。助手正文沿用现有部分文本/有效终态展示规则，不把半截流式文本标成完成回答。

### 4.1 时间区间拖选与联动

- 在总览空白处横向拖动超过 6 px 建立时间选区；点击片段只选中操作，不改变横轴。释放后保留选区，区间外片段变淡，列表只保留与区间相交且通过类型/阶段筛选的操作。
- 选区两端可调整，内部空白可平移；范围限制在当前展示域内，最小区间为 1 ms。正反向拖选等价，pointercancel 恢复原选区。边界可命中区域扩大，不改变条的时间长度。
- 相交按真实区间计算；零耗时记录按时刻是否落在闭区间判断。显示选区起止、跨度和匹配数；跨度不能冒充这些调用耗时之和。
- “全部时间”只清除时间范围，保留类型/阶段筛选。筛选后选中项若已不在结果中，关闭其详情；若键盘焦点原在详情内则返回时间总览，否则不抢焦点，并简短播报。
- 用户建立选区时冻结该展示域；新事件不推动选区，提示有新操作。清除范围才回到最新全长。原始服务端偏移不因缩放、筛选或类型切换而改变。
- 选区边界提供键盘 slider：左右键移动约 1%，Shift+左右键约 10%，Home/End 到合法端点；按范围最小值钳制。Escape 优先关闭详情，没有详情时清除选区。触屏区分横向拖选与纵向滚动，不接管全页滚动。

Harness 的拖选已实际观察；边界调整、内部平移和上述键盘规范是本项目明确补充的设计，不能写成该产品已经验证的能力。

## 5. 响应式与可访问交互

- 内容区域 ≥1080 px：选中后出现 340 px 右侧详情；720–1079 px：详情在列表下展开；小于 720 px：使用全宽 sheet。阈值按扣除侧栏/内边距后的可用内容区域计算。
- 深浅主题均验证 1440×900、1024×768、390×844；390 px 不出现页面横向溢出。手机只保留必要名称、状态、耗时，精确起止放进详情。
- tabs 使用键盘语义；阶段使用原生 button，Enter/Space 打开，Escape 关闭详情。普通详情不制造焦点陷阱，模态 sheet 才管理内部焦点。
- 时间图提供同内容可读列表，类型/详情 tabs 支持键盘，不依赖颜色、hover 或 canvas。范围起止使用可访问 slider；aria-live 只在拖动释放或键盘更改后播报范围，不逐帧播报。
- 当前阶段只使用轻微 opacity 动效，减少动态效果时静态显示。切换 tabs 不重发或取消 ask，不清空输入，滚动由用户控制。

## 6. 首版数据流与协议草案（尚未实现）

首版不建立独立 trace GET API，不引入数据库或基础设施。轨迹跟随已通过身份和 KB 权限校验的本次响应传递。浏览器只保留当前已加载问答；刷新、退出、身份变化或组件释放时清理，不写 localStorage、IndexedDB 或服务端历史表。

```
实际 QA 阶段生命周期
  ├─ 既有 OTel spans / metrics（沿用开关与采样）
  └─ 可选安全 observer（独立开关，不依赖 exporter）
       ├─ 同步 metadata.executionTrace 最终快照
       └─ 显式协商 trace-v1 的流式 trace 事件
                   ↓
        runId + stageId 更新当前页面轨迹
                   ↓
         分组时间线 → 手动选中的详情
```

observer 从真实开始/结束/重试/降级钩子生成投影，不能解析普通日志、预排动画或只接收 sampled spans 后宣称完整。须测试 OTel/exporter 关闭时仍有请求内轨迹。traceId 可空、仅供关联；runId 由服务端生成，代表单次执行，不是多轮会话 ID 或独立查询凭证。

### 6.1 同步与流式传输

支持轨迹的新客户端在功能启用后，对本次 ask 发送 X-RAG-Trace-Contract: trace-v1；流式同时保留 X-RAG-Stream-Contract: structured-v1。协商在发起 ask 时完成，与用户当前停留哪个 tab 无关，因此回答结束后再点开轨迹也有记录；切换 tab 不补发 ask。服务端不支持/未启用时，问答沿用现有行为，界面显示“本次未提供轨迹”。

同步路径通过 metadata.executionTrace 返回最终快照，不承诺处理中实时刷新。流式仅在显式协商后增加命名事件 trace，其中 kind 为 execution.start、stage.upsert、execution.snapshot，分别表达开始、阶段更新、最终采集快照。最终快照在既有 terminal 之前发送；原 text/terminal 字段、引用和业务语义不变，terminal 只发送一次，之后不再发送事件。

旧客户端绝不能收到新增 trace 事件，原 structured-v1 未知事件严格拒绝策略保持不变。新 parser 仅在协商模式识别 trace；坏 trace、超额或缺测使轨迹 PARTIAL，不把有效 text/terminal 改判错误。重复 terminal、terminal 后 text、破损 terminal 仍按原协议失败。若 SSE 写入本身失败，则按现有连接失败处理，不能借“采集失败不影响业务”宣称传输成功。

### 6.2 最小字段

| 数据 | 拟定字段及语义 |
| --- | --- |
| 公共信封 | schemaVersion=trace-v1、runId、seq、kind；seq 为单 run 单调递增序号 |
| 执行快照 | traceId 可空、captureStatus=COMPLETE/PARTIAL、elapsedMs、stages、reasonCode 可空、businessFinalState 可空 |
| 阶段 | stageId、parentStageId 可空、stage 固定枚举、status、startOffsetMs、endOffsetMs 可空、facts 白名单 |
| 阶段状态 | RUNNING/SUCCEEDED/FAILED/CANCELLED/SKIPPED；尚未结束不得填造 endOffsetMs |
| 安全事实 | requested/effective provider 受限枚举、attemptCount、retryCount、fallbackReason/errorCategory 固定枚举，以及真实存在的 selectedContextCount/usage |

操作类型、四阶段归属和一句说明由受版本管理的 stage→type/phase/template 映射投影，不新增任意自由文本字段。详情参数扩展仅按实际操作加入有界 topK/minScore/启用状态等白名单，不复制原始请求。上下文的可读来源和助手回答由前端同一 run 的已有授权响应关联，绝不因新增详情页签放开普通遥测的隐私限制。

时间来自同一执行起点的服务端单调时钟，统一为 ms，UI 再格式化。首版“服务端执行”限定为 RAGService 的实际生命周期，不包括此前认证/KB 授权、网络传输和后续历史写入；不能用轨迹完成证明历史已保存。浏览器等待时间不冒充服务端耗时；缺少真实计数或 usage 时显示“未提供”，不填 0。COMPLETE 仅表示采集完整，不代表业务成功或评测质量通过。

同一 stageId 幂等更新，旧 seq 不覆盖新状态。seq 缺口先标 PARTIAL，只有合法且自足的最终完整快照才能恢复 COMPLETE。快照不能替代业务 terminal；两者不一致时提示“执行记录不一致”，不得合成成功历史。

### 6.3 隐私、限额与生命周期

采集配置为 rag.execution-trace.enabled，通过 RAG_EXECUTION_TRACE_ENABLED 显式映射，与 rag.observability.* 独立。通用配置仍默认关闭；2026-10-27 用户授权调整日常启动配置后，start-backend.ps1 在加载 .env.local 后为未设置的开关补 true，显式 false 保持关闭。开启轨迹不新增模型调用，不改变检索、重排、prompt、citation、no-answer 默认行为或评测口径。

单 run 最多 128 阶段、256 条增量，单条增量净荷不超过 2 KiB，最终快照不超过 64 KiB，总轨迹净荷不超过 576 KiB，按 UTF-8 JSON 字节计，不含 HTTP/SSE framing。额度含开始/最终记录的预留位；超限停止细节增长，保留最终 PARTIAL/TRUNCATED 状态，不挤占回答 token 预算。observer 只进入有界收集器，由单一发送出口串行交付 trace/text/terminal，不能直接从并发阶段回调写 SSE；细节队列满时丢弃并标部分采集，不阻塞业务线程。前端同样校验边界，页面仅保留最近 20 条已结束记录及当前运行记录；淘汰后说明“本页记录已释放”，不自动补发 ask。

只传固定枚举、合法 ID、计数、布尔值和非负时间。question/prompt/answer/context/snippet、文件路径/标题、用户/租户身份、凭据、原始异常和 provider body 不进入 trace 净荷。问题和引用正文仍来自原授权响应。技术 ID 默认折叠；复制技术信息仅含白名单字段，不提供原始 JSON 转储。退出/身份变化清理选中项及迟到回调。

## 7. 状态与失败呈现

| 情况 | 用户看见什么 |
| --- | --- |
| 运行中 | 已收到阶段及“执行中”；客户端等待计时不冒充服务端精确耗时 |
| 正常完成 | 业务终态与真实阶段，默认没有异常警告或展开详情 |
| 缓存命中 | 实际准备记录与“命中缓存”，不画检索/生成成功条 |
| 无答案/不支持 | 显示业务终态与实际阶段，不把正常拒答标为系统故障 |
| 降级成功 | 保留“已完成”，旁边只有“1 项降级”入口，展开再看安全原因和替代路线 |
| 阶段失败 | 保留已完成记录，失败处使用小面积危险标记，不展示原始异常 |
| 客户端停止/断网 | “已停止接收 / 连接中断，服务端状态未确认”，不擅自把运行阶段改为 CANCELLED |
| 无轨迹/部分采集 | “本次未提供轨迹 / 轨迹不完整”，回答照常，不画占位成功步骤 |
| 历史页/旧记录 | 保留原回答和来源，说明“该记录未保存轨迹”，不承诺刷新恢复 |

## 8. 实施、验证与回滚

拟影响前端 ChatPanel、qaPresentation、useSSE/sseParser、局部 trace 组件/类型/主题；后端涉及 QAController 协商/响应投影、RAGServiceImpl 和阶段 observer 必要连接及测试。OTel 入口若增加 observer 钩子，须保留 tracing/metrics 关闭和 fail-open 契约。具体文件在写切片前按调用链确定，不顺手重构旧 ChatView 或其他页面。

先用标明模拟数据的封闭预览验证视觉/交互，再接真实钩子和协议。运行 Java 聚焦/telemetry 回归、前端状态/解析回归及含 vue-tsc 正式构建。浏览器覆盖深浅三视口、键盘/触屏替代、错误/降级/断连、tabs/输入保留、清理和无额外请求。真实 provider 验证须另外披露载荷、模型、次数、预算、重试与数据出站并获授权。

第二轮保留隔离、零网络的单 HTML 设计稿。正式实施已经完成组件、observer、同步快照和流式 trace 接线，本地证据见[接入记录](implementation-review.md)，不能用原型或合成测试宣称真实 provider 联调完成。服务端以 rag.execution-trace.enabled 独立控制采集；通过 start-backend.ps1 启动时默认开启，其他启动方式仍默认关闭，可显式设置 RAG_EXECUTION_TRACE_ENABLED=true 或启动参数 --rag.execution-trace.enabled=true。关闭时将环境变量设为 false 后重启；如需撤掉客户端协商，将 ChatPanel 的同步 includeTrace 和流式 onTrace 入口关闭，旧协议仍可使用。没有改受保护的本地配置。

## 决策记录

### D1：把细节放进选中后的详情

- **当时面临哪几个选择？** 可以像截图一样连续铺出调用与文字，也可以默认只看时间分布，再选中某一步。
- **最终选了谁 + 理由是什么？** 第二轮采用三色类型轨道加简短操作列表，细节仍按需展开。用户先看到活动分布，再读一句说明；四阶段保留作筛选，不把所有细节压成四根条。
- **其他方案的代价是什么？** 连续明细适合逐条审计，但每次铺满参数会分散注意力；单一进度条又看不出瓶颈，所以保留可展开的真实子阶段。

### D2：沿问答响应传轨迹，不建设独立轨迹后台

- **当时面临哪几个选择？** 可以查 Grafana/Tempo、增加持久轨迹 API，或沿本次授权响应传最小阶段事实。
- **最终选了谁 + 理由是什么？** 选响应内传递。当前首先需要看清这次问答，这条路线减少基础设施和跨资源鉴权工作。
- **其他方案的代价是什么？** Tempo 可能关闭、采样或过期；数据库/API 更适合长期回放，但增加保留、删除、权限和迁移成本。本版接受刷新不能恢复的边界，历史回放另立 change。

### D3：显式协商保护旧流式客户端

- **当时面临哪几个选择？** 可以直接向 structured-v1 塞新事件、全面放宽未知事件检查，或单独协商轨迹扩展。
- **最终选了谁 + 理由是什么？** 选 trace-v1 显式协商。旧 parser 会拒绝未知事件，未请求扩展时必须仍只收到 text/terminal。
- **其他方案的代价是什么？** 直接新增会让旧客户端报错；全面忽略未知事件会掩盖协议损坏。新模式只隔离辅助轨迹坏数据，业务终态仍严格验证。

### D4：应用轨迹独立于 OTel 采样，但复用实际事实

- **当时面临哪几个选择？** 可以只读导出 spans、另写一套模拟步骤，或让真实生命周期向可选 observer 提供受限事实。
- **最终选了谁 + 理由是什么？** 选 observer。用户不应因为 exporter 关闭就看见假步骤，也不应为打开界面被迫部署采集栈。
- **其他方案的代价是什么？** sampled spans 会缺测，模拟流程容易漂移；observer 仍有运行与维护开销，因此设独立开关、净荷上限和兼容回归，不新增模型调用。

### D5：保留真实时间与不确定性

- **当时面临哪几个选择？** 可以预排动画并把断开当取消，或只画已观察阶段，分开表达业务、采集和连接状态。
- **最终选了谁 + 理由是什么？** 选后者。轨迹用于判断真实过程，不能确认时必须明确留下空缺。
- **其他方案的代价是什么？** 固定动画更整齐，却会把缓存/失败演成完整流程。真实条可能短、重叠或缺失，所以用点击区域、详情和 PARTIAL 保证可读。

### D6：沿用现有工作台视觉和能力边界

沿用现有字体、主题、输入框与依赖。工具类表示真实 RAG 组件调用，并未新增 Agent 运行时；上传/索引、历史回放、Agent 自主工具编排与模型内部思维不在本 change 内。

### D7：颜色区分操作类型，状态使用独立标记

- **当时面临哪几个选择？** 可以继续统一灰条、为每个状态全条换色，或为工具/助手/上下文固定三种颜色。
- **最终选了谁 + 理由是什么？** 选择固定三色。用户能顺着颜色认出活动类型，失败时也不会丢掉操作身份；状态用小图标、文字和安全原因表达。
- **其他方案的代价是什么？** 单色难以扫读，整条随状态变色则会把工具与助手混淆。三色需要维护深浅主题对比度，因此同时保留类型文字与选中描边。

### D8：滑动选区只改变本页观察范围

- **当时面临哪几个选择？** 可以拖动后重跑请求、缩放后改写时间，或只在已有记录上建立可撤销筛选。
- **最终选了谁 + 理由是什么？** 选择本页筛选。拖动用于检查已经发生的事，不需要模型再回答一遍。
- **其他方案的代价是什么？** 重新请求会扩大成本且改变观察对象；自动追随运行域会让选区漂移，所以选区激活时冻结展示域，用户明确恢复全部时间后再跟上新记录。

### D9：分类详情复用现有授权内容

- **当时面临哪几个选择？** 可以照搬 Harness 的原始内容/Schema 页，也可以围绕 RAG 的工具参数、回答和来源组织详情。
- **最终选了谁 + 理由是什么？** 选择后者，并只复用当前授权响应里的可读内容；trace 继续只承载受限事实。
- **其他方案的代价是什么？** 直接把 prompt、上下文和模型内部思维塞进 trace 会扩大隐私和存储边界；统一 JSON 页也会重新造成文字堆积，所以按类型只显示有意义的页签。
