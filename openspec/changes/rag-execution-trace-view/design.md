# RAG 轨迹界面设计

## 💡 30秒人话设计主旨

现在用户只能看见答案，看不见系统把时间花在了哪里。我们把一次问答画成几条安静的时间线：先看结果、耗时和阶段分布，想追查时再点开某一步。醒目之处来自时间的位置和长度，详细说明只在需要时出现。本轮只完成设计；首版实施范围是当前页面内的单次问答，历史回放与上传索引另行规划。

## 1. 设计定位与参考边界

参考用户提供的 DeepSeek Harness 截图，保留“对话 / 轨迹入口、时间总览、按发生位置检查执行”的优点。截图中的长工具参数、密集逐行文本和多色同时强调不进入默认界面。不推断截图之外的功能或内部实现。

采用 minimalist-ui 的留白、少色和按需展开原则；字体、图标、背景和输入框沿用现有主题与依赖，不全站换肤，不增加字体/CDN/图标包。[现有主题变量](../../../rag-frontend/src/styles/variables.css)仍是实现事实源。

## 2. 信息层级与页面结构

| 层级 | 默认可见内容 | 用户想解决的问题 |
| --- | --- | --- |
| 入口 | 对话 / 轨迹；多条已加载问答时才出现“本次问答”选择器 | 我检查的是哪次请求？ |
| 摘要 | 最终业务状态、服务端执行耗时；存在异常时才显示“1 项降级”等数量入口 | 是否完成，花了多少时间？ |
| 时间线 | 最多四类一级分组：准备、检索、生成、校验；每行仅名称、状态、时间条、耗时 | 时间花在哪里？ |
| 详情 | 手动选中后的子阶段、起止偏移、实际调用/重试和安全原因；技术信息再折叠 | 具体发生了什么？ |

问答原文最多显示一行作为记录上下文，不重复铺出回答或引用片段。首屏不设置 KPI 卡片墙、日志终端、全局搜索、轮次/调用三套模式或工具按钮排。异常数大于零时提供“仅看异常”入口，只筛选本次已收到的记录，不发出新的问答或查询。

```
现有侧栏 | 对话  轨迹                       本次问答 ▾
         | 这一知识库如何处理检索降级？
         | 已完成                 服务端执行 4.82 s
         |              0         2          4.82 s
         | 准备     ✓   ━                     0.03 s
         | 检索     ✓    ━━━━                  0.79 s
         | 生成     ✓        ━━━━━━━━━━━━━━    3.71 s
         | 校验     ✓                      ━  0.29 s
         | 选中阶段后查看详情
         |             现有输入框保持可用
```

这些数值仅为模拟数据。浅色总览、深色选中详情和窄屏稿见 [visuals](visuals/README.md)。

## 3. 视觉规格：让时间关系成为特点

- 一级行高 48 px，二级行高至少 40 px，时间条高 6 px、圆角 3 px；横轴最多五个刻度，数值使用等宽数字，不逐 token 绘制标记。
- 成功阶段用中性色，选中阶段用现有 --rag-primary；降级和失败用小面积警示/危险色，并配合文字或符号，不把每行涂成不同颜色。承载信息的时间条与背景对比至少 3:1，普通正文至少 4.5:1。
- 一级标签 14–15 px，耗时 13 px，摘要结果 22–24 px，次要文本至少 12 px。沿用中文系统字体，说明使用完整短句。
- 使用 --rag-bg-page、--rag-bg-surface、--rag-border、--rag-text-primary/secondary，只增加 trace 局部 token；用描边和留白构建层级，不新增大面积渐变、发光、重阴影或粒子背景。
- 总览内容宽度不超过 1080 px，居中显示；时间条共享同一横轴，短阶段不能为了好看而改变时间比例。可给短条增加透明点击区域。
- 已结束请求固定横轴。运行中横轴按 1/2/5 倍数向右扩展，不移动原点；一级耗时使用真实区间，绝不简单相加子阶段。

## 4. 实际阶段如何压缩与展开

| 一级分组 | 实际来源 | 边界 |
| --- | --- | --- |
| 准备 | 实际缓存检查；未来若补路由记录，须由真实路由生命周期产生 | 只在有记录时出现，不假设每次都有路由 |
| 检索 | retrieval 下的 query embedding、dense、keyword、fusion、rerank | 默认一行，展开后保留父子顺序与重叠 |
| 生成 | generation 下的 prompt build、LLM request | 显示真实生成区间；重试放入详情计数/有限子项 |
| 校验 | citation validate | 不能将校验调用成功解释为答案质量已通过 |

分组只是展示投影，原 stageId/parentStageId 和时间必须保留。未知实际阶段以“其他阶段”显示，并明确分类边界。未执行不造条；服务端明确报告因缓存命中跳过时，可在详情说明“未执行：缓存命中”，没有事实时只能说“未记录”。

第一次打开只看总览，详情关闭。点击条或行选中同一阶段，再次点击不反复折叠；用明确的关闭按钮关闭详情。新事件不能抢走手动选择、焦点或滚动位置。“仅看异常”保留完整横轴，说明筛选后的数量。

## 5. 响应式与可访问交互

- 内容区域 ≥1120 px：选中后出现 320 px 右侧详情，未选中时总览居中。阈值按内容区域计算，不能把侧栏宽度算进来。
- 内容区域 720–1119 px：详情在选中行后展开；小于 720 px：保留相对时间短条，详情进入全宽 sheet，关闭后焦点回到原阶段按钮。
- 深浅主题均验证 1440×900、1024×768、390×844；390 px 不出现页面横向溢出。手机只保留必要名称、状态、耗时，精确起止放进详情。
- tabs 使用键盘语义；阶段使用原生 button，Enter/Space 打开，Escape 关闭详情。普通详情不制造焦点陷阱，模态 sheet 才管理内部焦点。
- 时间图提供同内容的可读列表，不依赖颜色、hover 或 canvas。aria-live 使用 polite，只播报阶段变化/最终结果，不逐 token 或每帧播报耗时。
- 当前阶段只使用轻微 opacity 动效，减少动态效果时静态显示。切换 tabs 不重发或取消 ask，不清空输入，滚动由用户控制。

## 6. 首版数据流与协议草案（尚未实现）

首版不建立独立 trace GET API，不引入数据库或基础设施。轨迹跟随已通过身份和 KB 权限校验的本次响应传递。浏览器只保留当前已加载问答；刷新、退出、身份变化或组件释放时清理，不写 localStorage、IndexedDB 或服务端历史表。

```
实际 QA 阶段生命周期
  ├─ 既有 OTel spans / metrics（沿用开关与采样）
  └─ 可选安全 observer（独立开关，不依赖 exporter）
       ├─ 同步 metadata.executionTrace 最终快照
       └─ 显式协商 trace-v1 的流式 trace 事件
                   ↓
        runId + stageId 更新当前页面轨迹
                   ↓
         分组时间线 → 手动选中的详情
```

observer 从真实开始/结束/重试/降级钩子生成投影，不能解析普通日志、预排动画或只接收 sampled spans 后宣称完整。须测试 OTel/exporter 关闭时仍有请求内轨迹。traceId 可空、仅供关联；runId 由服务端生成，代表单次执行，不是多轮会话 ID 或独立查询凭证。

### 6.1 同步与流式传输

支持轨迹的新客户端在功能启用后，对本次 ask 发送 X-RAG-Trace-Contract: trace-v1；流式同时保留 X-RAG-Stream-Contract: structured-v1。协商在发起 ask 时完成，与用户当前停留哪个 tab 无关，因此回答结束后再点开轨迹也有记录；切换 tab 不补发 ask。服务端不支持/未启用时，问答沿用现有行为，界面显示“本次未提供轨迹”。

同步路径通过 metadata.executionTrace 返回最终快照，不承诺处理中实时刷新。流式仅在显式协商后增加命名事件 trace，其中 kind 为 execution.start、stage.upsert、execution.snapshot，分别表达开始、阶段更新、最终采集快照。最终快照在既有 terminal 之前发送；原 text/terminal 字段、引用和业务语义不变，terminal 只发送一次，之后不再发送事件。

旧客户端绝不能收到新增 trace 事件，原 structured-v1 未知事件严格拒绝策略保持不变。新 parser 仅在协商模式识别 trace；坏 trace、超额或缺测使轨迹 PARTIAL，不把有效 text/terminal 改判错误。重复 terminal、terminal 后 text、破损 terminal 仍按原协议失败。若 SSE 写入本身失败，则按现有连接失败处理，不能借“采集失败不影响业务”宣称传输成功。

### 6.2 最小字段

| 数据 | 拟定字段及语义 |
| --- | --- |
| 公共信封 | schemaVersion=trace-v1、runId、seq、kind；seq 为单 run 单调递增序号 |
| 执行快照 | traceId 可空、captureStatus=COMPLETE/PARTIAL、elapsedMs、stages、reasonCode 可空、businessFinalState 可空 |
| 阶段 | stageId、parentStageId 可空、stage 固定枚举、status、startOffsetMs、endOffsetMs 可空、facts 白名单 |
| 阶段状态 | RUNNING/SUCCEEDED/FAILED/CANCELLED/SKIPPED；尚未结束不得填造 endOffsetMs |
| 安全事实 | requested/effective provider 受限枚举、attemptCount、retryCount、fallbackReason/errorCategory 固定枚举，以及真实存在的 selectedContextCount/usage |

时间来自同一执行起点的服务端单调时钟，统一为 ms，UI 再格式化。首版“服务端执行”限定为 RAGService 的实际生命周期，不包括此前认证/KB 授权、网络传输和后续历史写入；不能用轨迹完成证明历史已保存。浏览器等待时间不冒充服务端耗时；缺少真实计数或 usage 时显示“未提供”，不填 0。COMPLETE 仅表示采集完整，不代表业务成功或评测质量通过。

同一 stageId 幂等更新，旧 seq 不覆盖新状态。seq 缺口先标 PARTIAL，只有合法且自足的最终完整快照才能恢复 COMPLETE。快照不能替代业务 terminal；两者不一致时提示“执行记录不一致”，不得合成成功历史。

### 6.3 隐私、限额与生命周期

采集配置拟为 rag.execution-trace.enabled，默认关闭，与 rag.observability.* 独立；最终绑定名在实现时核对。开启轨迹不新增模型调用，不改变检索、重排、prompt、citation、no-answer 默认行为或评测口径。

单 run 最多 128 阶段、256 条增量，单条增量净荷不超过 2 KiB，最终快照不超过 64 KiB，总轨迹净荷不超过 576 KiB，按 UTF-8 JSON 字节计，不含 HTTP/SSE framing。额度含开始/最终记录的预留位；超限停止细节增长，保留最终 PARTIAL/TRUNCATED 状态，不挤占回答 token 预算。observer 只进入有界收集器，由单一发送出口串行交付 trace/text/terminal，不能直接从并发阶段回调写 SSE；细节队列满时丢弃并标部分采集，不阻塞业务线程。前端同样校验边界，页面仅保留最近 20 条已结束记录及当前运行记录；淘汰后说明“本页记录已释放”，不自动补发 ask。

只传固定枚举、合法 ID、计数、布尔值和非负时间。question/prompt/answer/context/snippet、文件路径/标题、用户/租户身份、凭据、原始异常和 provider body 不进入 trace 净荷。问题和引用正文仍来自原授权响应。技术 ID 默认折叠；复制技术信息仅含白名单字段，不提供原始 JSON 转储。退出/身份变化清理选中项及迟到回调。

## 7. 状态与失败呈现

| 情况 | 用户看见什么 |
| --- | --- |
| 运行中 | 已收到阶段及“执行中”；客户端等待计时不冒充服务端精确耗时 |
| 正常完成 | 业务终态与真实阶段，默认没有异常警告或展开详情 |
| 缓存命中 | 实际准备记录与“命中缓存”，不画检索/生成成功条 |
| 无答案/不支持 | 显示业务终态与实际阶段，不把正常拒答标为系统故障 |
| 降级成功 | 保留“已完成”，旁边只有“1 项降级”入口，展开再看安全原因和替代路线 |
| 阶段失败 | 保留已完成记录，失败处使用小面积危险标记，不展示原始异常 |
| 客户端停止/断网 | “已停止接收 / 连接中断，服务端状态未确认”，不擅自把运行阶段改为 CANCELLED |
| 无轨迹/部分采集 | “本次未提供轨迹 / 轨迹不完整”，回答照常，不画占位成功步骤 |
| 历史页/旧记录 | 保留原回答和来源，说明“该记录未保存轨迹”，不承诺刷新恢复 |

## 8. 实施、验证与回滚

拟影响前端 ChatPanel、qaPresentation、useSSE/sseParser、局部 trace 组件/类型/主题；后端涉及 QAController 协商/响应投影、RAGServiceImpl 和阶段 observer 必要连接及测试。OTel 入口若增加 observer 钩子，须保留 tracing/metrics 关闭和 fail-open 契约。具体文件在写切片前按调用链确定，不顺手重构旧 ChatView 或其他页面。

先用标明模拟数据的封闭预览验证视觉/交互，再接真实钩子和协议。运行 Java 聚焦/telemetry 回归、前端状态/解析回归及含 vue-tsc 正式构建。浏览器覆盖深浅三视口、键盘/触屏替代、错误/降级/断连、tabs/输入保留、清理和无额外请求。真实 provider 验证须另外披露载荷、模型、次数、预算、重试与数据出站并获授权。

本轮仅做规划结构、相对链接、场景覆盖、静态稿和 DocAndScope，不运行无关业务测试，不把静态稿称作浏览器验收。回滚先关闭新开关与客户端协商；旧同步/structured-v1 及历史沿原规则使用。前后端混合版本、未知 trace、无轨迹均需兼容测试。

## 决策记录

### D1：把细节放进选中后的详情

- **当时面临哪几个选择？** 可以像截图一样连续铺出调用与文字，也可以默认只看时间分布，再选中某一步。
- **最终选了谁 + 理由是什么？** 选后者。用户先知道结果与时间，再决定检查哪里；四类分组让 RAG 阶段更容易辨认。
- **其他方案的代价是什么？** 连续明细适合逐条审计，但每次铺满参数会分散注意力；单一进度条又看不出瓶颈，所以保留可展开的真实子阶段。

### D2：沿问答响应传轨迹，不建设独立轨迹后台

- **当时面临哪几个选择？** 可以查 Grafana/Tempo、增加持久轨迹 API，或沿本次授权响应传最小阶段事实。
- **最终选了谁 + 理由是什么？** 选响应内传递。当前首先需要看清这次问答，这条路线减少基础设施和跨资源鉴权工作。
- **其他方案的代价是什么？** Tempo 可能关闭、采样或过期；数据库/API 更适合长期回放，但增加保留、删除、权限和迁移成本。本版接受刷新不能恢复的边界，历史回放另立 change。

### D3：显式协商保护旧流式客户端

- **当时面临哪几个选择？** 可以直接向 structured-v1 塞新事件、全面放宽未知事件检查，或单独协商轨迹扩展。
- **最终选了谁 + 理由是什么？** 选 trace-v1 显式协商。旧 parser 会拒绝未知事件，未请求扩展时必须仍只收到 text/terminal。
- **其他方案的代价是什么？** 直接新增会让旧客户端报错；全面忽略未知事件会掩盖协议损坏。新模式只隔离辅助轨迹坏数据，业务终态仍严格验证。

### D4：应用轨迹独立于 OTel 采样，但复用实际事实

- **当时面临哪几个选择？** 可以只读导出 spans、另写一套模拟步骤，或让真实生命周期向可选 observer 提供受限事实。
- **最终选了谁 + 理由是什么？** 选 observer。用户不应因为 exporter 关闭就看见假步骤，也不应为打开界面被迫部署采集栈。
- **其他方案的代价是什么？** sampled spans 会缺测，模拟流程容易漂移；observer 仍有运行与维护开销，因此设独立开关、净荷上限和兼容回归，不新增模型调用。

### D5：保留真实时间与不确定性

- **当时面临哪几个选择？** 可以预排动画并把断开当取消，或只画已观察阶段，分开表达业务、采集和连接状态。
- **最终选了谁 + 理由是什么？** 选后者。轨迹用于判断真实过程，不能确认时必须明确留下空缺。
- **其他方案的代价是什么？** 固定动画更整齐，却会把缓存/失败演成完整流程。真实条可能短、重叠或缺失，所以用点击区域、详情和 PARTIAL 保证可读。

### D6：沿用现有工作台视觉和能力边界

沿用现有字体、主题、输入框与依赖，避免轨迹功能牵动全站换肤。上传/索引、历史回放、Agent 工具面板与模型内部思维均不在本 change 内，不以静态稿宣称已经具备。
