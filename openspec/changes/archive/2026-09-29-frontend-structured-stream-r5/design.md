# R5 设计

## 实现

现有 `useSSE` 保持唯一网络流入口，新增严格的结构化事件解析器。请求设置 `X-RAG-Stream-Contract: structured-v1`，只把 `event: text` 的 data 当回答文字；`event: terminal` 必须是符合 C21 版本、状态和字段形状的 JSON，且全流只能有一个。未知事件、缺失或重复 terminal、终态后文本、损坏 JSON 均视为协议/传输不完整，不推断业务成功。客户端 abort 优先报告本地停止接收。

聊天页仅从有效 terminal 取 final state、reason、citations；非 `ANSWER` 及错误清空来源。保留已收到的部分文字并标明不可作为完整回答。只有 `ANSWER` 通知历史列表刷新。终态展示不把 usage 的估计 token 说成 provider 实耗。

## 验证

合成流覆盖网络任意分帧、UTF-8、多行 data、`ANSWER` 来源、非答案、重复/缺失/损坏 terminal、terminal 后文本和 abort；运行 `npm test`、含 `vue-tsc` 的 `npm run build` 与 `git diff --check`。真实联调单独验收。

## 决策记录

### 决策 1：如何接入新协议
- **面临的选择**：另建 SSE client；替换现有流入口；在现有 `useSSE` 增加版本化解析。
- **选了哪个 + 为什么**：复用现有流入口并显式协商，保留单一网络请求与旧格式兼容。
- **放弃的代价**：另建 client 会复制鉴权和取消逻辑；直接替换会破坏旧调用。

### 决策 2：何时认定回答完成
- **面临的选择**：连接自然结束即成功；最后一个文本块即成功；只认可唯一有效 terminal。
- **选了哪个 + 为什么**：只认可唯一有效 terminal，符合 C21 对断流和业务终态的定义。
- **放弃的代价**：按连接或文本推断会把部分输出和无答案误报为成功。

### 决策 3：何时展示来源和刷新历史
- **面临的选择**：流结束即展示/刷新；再发同步 ask 补来源；仅用本次 `ANSWER` terminal 的来源并刷新。
- **选了哪个 + 为什么**：只使用本次有效 `ANSWER` terminal，来源与回答属于同次执行。
- **放弃的代价**：流结束即成功会误报非答案；补 ask 会增加调用、费用和不一致历史。

### 决策 4：为何把真实联调放在独立授权阶段
- **面临的选择**：离线接入后直接发真实流并将 abort 称为服务端取消；先完成离线接入，真实调用按独立授权验收。
- **选了哪个 + 为什么**：先完成离线接入，真实 provider 调用有独立出站、费用和历史副作用，另获授权后再联调；断连也无法保证 terminal 送达。
- **放弃的代价**：直接调用越过外调授权；把 abort 当取消会误述服务端和费用状态。
