# 头像与个人资料编辑设计

## 💡 30秒人话设计主旨

将“看资料”扩展成“编辑自己的资料”，同时保留现有浮层。头像、昵称和邮箱先作为草稿预览，点保存后才一次写入服务端；失败就保留草稿，结果不明确就读回核对，不把本地预览说成保存成功。登录名与工作空间不允许从这个表单修改，避免改资料时误改身份或权限。

## 1. 用户能看到什么

沿用当前账户栏目与现代下拉视觉，不新建个人中心路由。资料编辑区排在工作空间说明之前；退出登录仍放在最下方，避免与保存并列。

| 区域 | 首版设计 |
| --- | --- |
| 头像 | 64 px 圆形展示，旁边“更换头像”；已有头像时显示“移除头像”。选择后提供本地预览及“尚未保存”文字；移除在保存前也只是草稿操作。 |
| 登录用户名 | 只读文本与“用于登录，暂不支持修改”说明。 |
| 显示昵称 | 可编辑，选填，最多 50 个 Unicode 码点；空值回退到登录用户名展示。 |
| 邮箱 | 可编辑，选填，最长 100 字符；空白清为 null。说明“仅作为资料邮箱，当前不用于登录或找回密码”。不展示已验证徽章。 |
| 保存区 | “取消／保存修改”，有变化时显示未保存状态。提交期间保留按钮文字并显示进行中状态，阻止重复提交；无变化不发请求。 |
| 工作空间 | 保留当前真实归属与可见范围，只读，不随资料编辑改变。 |

鼠标或键盘选文件均可；文件输入有清晰名称，格式/大小错误紧邻头像显示。保存失败不只弹一个 toast，输入框错误有 label、aria-describedby 与焦点定位。窄屏上下排列，保存区始终能滚动到达。

侧栏、账户摘要显示 `displayName || username`，初始字母使用该展示名；表单始终保留独立“登录用户名”，不把昵称改名冒充登录名变更。新头像加载失败时回退字母，不影响页面。

## 2. 编辑、保存与关闭

1. 打开账户栏目，从服务端读取完整资料作为基线和草稿。加载失败显示重试；此时不展示可用的保存按钮，不从旧演示页或 localStorage 补假字段。
2. 修改字段、选择或移除头像只改变草稿。取消恢复服务端基线并释放本地预览 URL，不发写请求；侧栏和其他资料展示在成功保存前不变。
3. 点保存先校验，校验通过再提交一次。请求期间保持表单和加载状态，防止重复点击；同时修改的昵称/邮箱/头像在一个事务内成功或一起回滚。
4. 保存成功后立即更新昵称、侧栏与头像；已通过服务器保存确认的头像可从本次规范 PNG 直接发布到共享内存，不等待第二次下载。不改 Token、sessionRevision、工作空间、问答输入或正在接收的 SSE。
5. 根据 2026-10-28 用户纠正，资料保存没有单独的“保存草稿”步骤，也不向用户展示服务器副本或核对面板。字段错误紧邻输入框展示；网络、服务失败或版本冲突只显示清楚的失败/重试提示，保留当前输入并允许继续编辑。响应不明确时不假报成功、不自动重发写请求；用户再次点击保存时，客户端内部先读取最新版本再提交。
6. 关闭、遮罩、Escape 或切换栏目时，若有尚未保存的修改，在同一浮层内确认“继续编辑／放弃修改”；保存进行中避免中断。取消确认后焦点回到合理控件。没有修改时沿用原关闭行为。
7. 退出或换号立即清理该账号草稿、预览与 Blob URL。旧请求的成功、失败和 finally 都必须核对 sessionRevision 和资料读取 generation，不能回填新账号。

账户栏目页脚为“个人资料保存成功后立即生效”；其他栏目继续使用“偏好即时生效，仅保存在当前浏览器”。本地“重置偏好”不重置头像、昵称或邮箱。

## 3. 候选接口与返回数据

所有接口认证与取身份沿用 CurrentUserService/RequestIdentity；不接受客户端 userId、tenantId、username、角色或组织参数来指定目标用户。SQL 同时约束 user.id、tenant_id，以及用户/租户 enabled=1、deleted=0。读取/更新只面向自己，不增加可枚举的用户头像地址。

| 方法与路径 | 请求 | 成功返回 |
| --- | --- | --- |
| GET /api/account/profile | 无目标身份参数 | ApiResponse 包装完整资料，Cache-Control: no-store。 |
| PUT /api/account/profile | multipart 的 profile JSON + 可选 avatar 文件 | 200 + 保存后的完整资料；revision 必须匹配。 |
| GET /api/account/profile/avatar | Bearer 认证，无用户选择参数 | 当前用户头像的 PNG 二进制，no-store、nosniff；不存在为 404。 |

完整资料 DTO 拟为 `{ id, username, displayName, email, hasAvatar, revision }`。revision 来自 user.version，作为乐观锁；id 只读返回，不能用于保存选择。PUT 的 profile 仅允许 `{ displayName, email, expectedRevision, avatarAction }`，avatarAction 为 KEEP/REPLACE/REMOVE。REPLACE 必须且只能带一个头像文件，其他动作禁止附带文件。拒绝未知写入字段，不做任意属性绑定。

固定错误包括 PROFILE_VALIDATION_FAILED/400、PROFILE_EMAIL_UNAVAILABLE/409、PROFILE_REVISION_CONFLICT/409、PROFILE_AVATAR_TOO_LARGE/413、PROFILE_AVATAR_UNSUPPORTED/415、PROFILE_AVATAR_INVALID/400；未认证沿用认证错误。明确验证失败或冲突不得部分写入；服务端非确定性失败由客户端读回核对。日志只记安全错误枚举、内部 ID、计数与耗时，不记录邮箱、昵称、图片、原始文件名或异常正文。

邮箱沿用现有全局唯一索引语义，去首尾空白但不擅自改写大小写；空字符串转 null。输入格式与上限在服务端再校验，唯一性由数据库兜底，冲突只返回邮箱不可用，不透露占用者身份。

## 4. 数据保存与头像处理

在 user 表新增 display_name（VARCHAR(50)，可空）与 avatar_data（MEDIUMBLOB，可空），复用已有 email 与 version。头像统一存为 PNG，无需保存上传文件名、外部 URL 或本地路径。迁移编号以实现时最新 Flyway 序号为准，本轮扫描最新为 V13；不修改旧迁移或种子数据。

资料查询投影不读取 password_hash，也不读取 avatar_data 全量，只计算 hasAvatar；头像二进制只由专用接口查询。AuthUser 原有认证投影保持不带图片，避免登录与每次请求搬运图片。保存使用 user.version CAS，同时递增 version、updated_at，匹配不到时重新区分已失效身份与版本冲突。重名资料保存不改 username、tenant_id、密码、角色、enabled 或 deleted。

头像的产品约束为 JPG/PNG、原文件不超过 2 MiB。浏览器按实际显示方向生成居中的 256×256 方形 PNG，供圆形预览和提交；首版不提供裁剪器。服务端独立检查实际字节、文件头和解码格式，不信任扩展名/MIME；先检查尺寸（单边不超过 4096、总像素不超过 1600 万），再解码并规范为 256×256 PNG，去掉原始元数据；最终图片不超过 512 KiB。SVG、GIF、WebP、外链与任意文件均不接收。非法图片和超限文件在任何资料写入前拒绝。

使用现有 JDK 图像处理与数据库，不加图像库、对象存储或外部图床。小头像直接随资料事务保存，避免文件已上传但资料保存失败产生孤儿资源；代价是每账号最多增加一张有上限的图片，备份体积增大。若未来用户量需要对象存储，另开迁移方案。

头像由前端已有认证请求客户端以 Blob 读取，不能把 Token 放在 URL 或用无认证的 img 地址获取私有内容。共享头像状态只在内存保留；新图加载后才替换旧图，替换/退出/卸载时释放 Object URL。

## 5. 与登录、刷新和已有上下文的兼容

/api/session/context 的 userInfo 添加可选 displayName、hasAvatar、profileRevision，原 id/username/email 与 workspace 字段保持。老前端忽略额外字段；新前端在资料接口不可用时保持原只读视图并明确提示，不能显示假保存。

登录与 refresh DTO/JWT 不新增头像或昵称，身份仍基于 username/userId/tenantId；共享上下文负责恢复展示资料。成功保存不会轮换凭据或重建问答页。新客户端按资料 revision 合并同一账号状态；晚到的旧上下文快照不能用旧邮箱/头像标记覆盖已保存的新版本。没有 revision 的旧响应不能覆盖已经确认的新资料版本；换号仍以会话序号优先隔离。

真实账号刷新恢复、跨浏览器读取需要同一后端数据库读回证明；单元测试、本地 Blob 预览或模拟“保存成功”不能作为持久化验收。

## 6. 验收与实施边界

- 后端：自己账号成功读写、禁用/删除身份、跨账号/租户目标伪造、字段白名单、邮箱冲突、版本冲突、图片格式/大小/尺寸、原子回滚、只读认证投影不带图片与日志脱敏。
- 前端：有/无头像、加载/保存/校验/结果未知、取消、放弃确认、对象 URL 清理、旧响应与换号、页脚范围、侧栏更新、刷新恢复，及偏好重置/问答/SSE 保持。
- 数据：迁移与真实 MySQL 约束/事务/Blob 读回使用隔离的 MySQL/Testcontainers；环境不可用时明确未验，不能用 H2/mock 宣称真实迁移通过。不对当前实际账号或真实数据库写入。
- 工程：聚焦后相称 Maven，前端相关/全量测试、包含 vue-tsc build、DocAndScope/SensitiveLogs；深浅/390/320 px 浏览器键盘与真实文件输入流程。实体设备、读屏、手机照片方向及真实持久化分别记录。

本方案已获用户确认，接口、迁移文件与表单已实现，本地验证见[实施记录](implementation-review.md)。settings-modal-preferences 仍待用户审阅。本轮未执行实际数据库迁移或账号写入；提交、部署、接受与归档仍需对应授权。

## 决策记录

### D1：昵称与登录用户名分开
用户选择编辑头像、显示昵称和邮箱，用户名保持只读。直接改 username 会牵动当前按用户名重新加载身份的 refresh 流程；单独昵称能改变展示而不改变登录身份。

### D2：显式保存与统一事务
- **当时面临哪几个选择？** 可以逐项自动保存，分别上传图片和保存文本，或作为一个资料草稿统一提交。
- **最终选了谁及理由？** 统一草稿与一次提交，用户能预览和取消，图片与文本不会只成功一半。
- **其他方案的代价是什么？** 自动保存难以解释取消；分别写入需要补偿与孤儿文件处理。本方案需要脏表单确认和请求结果核对。

### D3：小头像存数据库
- **当时面临哪几个选择？** 本地文件、外部对象存储或有严格大小上限的数据库二进制。
- **最终选了谁及理由？** 选数据库，当前原型没有头像存储契约，可复用事务和备份，不引入服务或费用。
- **其他方案的代价是什么？** 文件需处理路径/部署卷/清理，对象存储增加基础设施；数据库则增加存储体积，必须限定图片大小且不能进入认证查询。

### D4：邮箱保持资料用途
本轮确认邮箱编辑，但没有验证/找回邮件能力，因此只作为资料邮箱保存，不扩展为登录别名或恢复凭据。登录名、密码及现有认证语义沿用。

### D5：版本冲突与结果未知如实处理
使用已有 user.version 防止无意覆盖旧资料；不把相同文本或 revision 增长推断成头像一定保存成功。按用户 2026-10-28 的纠正，失败保留输入，去掉用户手动核对流程；再次保存时客户端内部读取最新版本，只有用户明确点击才再次提交。

### D6：保存即时生效，并补齐生产配置回归
用户指出保存头像和昵称就应立即生效。此次复现发现，普通 MyBatis 测试通过，但生产 MyBatis-Plus 会把顶层 byte[] 参数作为批量对象数组转换，导致带头像保存返回 500。头像参数改为带 data 属性的值对象，SQL 仍按 BLOB 写入同一事务；新增真实 Tomcat HTTP + 生产 MyBatis-Plus 配置 + 隔离 H2 测试，避免仅用 MockMvc 和普通 MyBatis 产生错误信心。前端在 200 确认后立即发布本次头像和昵称，失败不再要求用户管理“草稿核对”。
