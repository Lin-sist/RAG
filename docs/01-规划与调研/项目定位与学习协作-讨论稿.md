目前最需要解决的问题，是项目实现的复杂度已经超过项目主人能够解释和验证的范围。下一阶段先把已有 RAG 变成能亲自理解、修改和排查的作品，再根据具体使用问题决定是否增加功能。求职展示、技术学习和 AI 协作都围绕这一目标展开。

## 1. 已确认的目标与现实约束

以下内容来自本次用户回答，描述当前起点，不是能力测评结论。

| 事项 | 当前共识 |
| --- | --- |
| 首要收益 | 寻找第一段实习，目标偏向 AI 应用相关的业务代码开发。 |
| 学习目标 | 逐步掌握项目核心技术，能够参与设计决策，并在面试中解释实现、取舍和故障定位。 |
| 当前起点 | 用户自述各项技术基础与独立开发实践较弱，尚不能独立解释、修改和诊断完整核心链路。面试题目只作为参考，不据此推断每一道题的表现。 |
| 开发方式 | 继续使用 AI 辅助开发；愿意在核心任务里先表达判断，再操作、验证和复述。逆向理解已有项目同样算学习。 |
| 语言主线 | Java 为主；Python 先用于阅读和修改评测脚本，不同时展开两套完整学习路线。 |
| 应用方向 | 优先探索开发者项目文档查询与上手场景。当前没有真实用户和已选定的真实语料，因此场景价值仍待验证。 |
| 技术兴趣 | 分块、混合检索、重排与失败诊断，以及引用、拒答、评测和实验设计。 |

| 资源条件 | 现有免费 NVIDIA NIM 模型可以使用，但稳定性有限；优先复用现有工具，不因追逐技术名词增加依赖和基础设施。 |

此前讨论过研究与开源方向，后续澄清将近期优先级收敛为：求职收益 → 核心技术掌握 → 有边界的应用与开源展示。时间不是主要约束，但每次迭代应控制新增的理解负担。

## 2. 项目定位与范围建议

项目现有能力口径继续沿用：**可运行、可评测的模块化 RAG 工程原型**。具体已实现能力及证据边界以 [项目上下文](../../openspec/project.md)、当前代码和已接受规格为准。

面向下一阶段，建议把应用假设表述为：

> 帮助开发者在一组明确范围的项目文档中查找信息、查看依据；证据不足时给出清楚的无结果或拒答反馈。同时用这条链路学习 Java、RAG 和评测方法。

这个定位需要通过实际问题验证。可以从自己真正需要查阅的仓库文档，或范围清楚的公开项目文档开始；先人工确认问题、答案所在位置和资料版本，再比较直接阅读、关键词搜索和 RAG 的效果。如果简单方法已经足够，应接受缩小 RAG 的用途。

建议暂缓新增大功能，保留必要修复和已有主路径的收口工作。旧 [迭代蓝图](../90-历史归档/2026-08_长期迭代蓝图v6.md) 中的高级路由、来源联邦、长任务研究、受控动作与规模化部署，先作为后续候选方向讨论；本文不撤销历史批准，也不把这些候选项变成近期毕业条件。

重新考虑某项扩展时，至少应说清：哪个具体问题反复出现、现有方式为什么不足、怎样验证改进，以及新增维护和学习成本是否值得。

“对标 2027”在这里是方向参考，不是要求个人项目追齐所有企业平台能力，也不存在本次调研已经确认的统一行业毕业标准。

## 3. 建议的推进顺序

按掌握情况推进，不预设必须完成的周数；各阶段中的开发任务仍按仓库规则分级。

| 阶段 | 主要工作 | 进入下一阶段前应获得的证据 |
| --- | --- | --- |
| 先理解一条链路 | 从同步问答入口开始，跟踪请求对象、服务调用和一个明确的返回分支。遇到 Java、HTTP、集合或测试概念时，结合当前代码补学。 | 能画出这段数据流，找到关键代码，预测至少一个分支，并亲自操作相关验证。 |
| 明确一个使用场景 | 选择小范围文档和实际查阅问题，确认资料来源、答案依据与范围外问题；比较直接阅读、关键词搜索和 RAG。 | 能说明 RAG 帮助了什么、没有帮助什么；没有真实用户时如实标为个人试用或场景假设。 |
| 做一次有边界的改进 | 从实际失败案例中选择一个问题，只检验一个主要假设，例如分块是否丢失必要上下文。 | 能解释方案选择，展示相同条件下的对照与失败分析；结果允许提升、持平或回退。 |
| 整理作品并阶段收口 | 整理启动与演示说明、能力边界、关键设计和验证证据，并练习项目深挖。 | 达到第 7 节的停止标准后暂停功能扩张，把精力转向学习巩固、求职和真实反馈。 |

实验必须遵守现有评测约定：不回改历史冻结证据，不为评测题目定制生产行为；新场景、新数据或新源码所需的评测应使用适当的新版本记录。真实外部调用仍需按现行规则披露并取得授权。

## 4. 采用两种协作节奏

现有流程已经关注设计、范围、验证和回退。新增的重点，是在核心学习任务中确认项目主人是否掌握了这部分行为。

- **核心学习任务**：问答、检索、引用、拒答、评测，以及准备在简历中重点讲述的能力，采用下表的完整学习循环。
- **常规交付任务**：已经理解的重复工作、局部文案和机械整理，按现行授权连续完成，不逐项增加人工等待。

学习中的停顿用于让用户预测、操作和解释，不等同于新增工程审批。纯阅读和教学不自动创建 OpenSpec change；涉及实际改动时，仍以 AGENTS.md 的 Type A/B/C 规则为准。

| 步骤 | 用户参与什么 | AI 协助什么 | 本轮应留下什么 |
| --- | --- | --- | --- |
| 1. 确定问题 | 说明具体输入、期望行为，以及本轮想学会什么；确认做到哪里结束。 | 帮助缩小范围，查明现有实现和缺失信息。 | 一个工程问题和一个学习目标。 |
| 2. 预测行为 | 先说输入从哪里进入、经过哪些处理、预计得到什么结果。 | 提供最小必要调用链和关键代码；基础不足时先给一个例子，再换相似输入让用户预测。 | 一次预测及其与代码行为的对照。 |
| 3. 讨论取舍 | 先说明选择、理由、接受的代价与重新考虑的条件。 | 解释真实候选方案、约束和证据；没有实质取舍时不编造选项。 | 区分事实与假设的决策说明。 |
| 4. 完成小改动或实验 | 操作一个与学习目标有关的环节，例如修改输入、补判断、看断点或调整实验参数。 | 承担实现与机械工作，必要时提供代码骨架，逐步减少提示。 | 一个能解释输入输出的小行为变化，或一次可复现观察。 |
| 5. 检查证据 | 解释一个关键测试为什么应当成功，并预测改变条件后的行为。 | 运行适用检查，展示结果和限制；测试预期应来自需求与契约。 | 实际验证结果，不能只留下“AI 说通过”。 |
| 6. 复述与追问 | 暂时不看 AI 总结，说明问题、实现、取舍、证据和限制，再回答一个变化条件。 | 根据回答纠错和追问，先给提示，再补充解释。 | 本轮已经掌握的内容和仍需练习的内容。 |

工程验收和学习验收分别判断：一项修复可以已正确交付，但用户仍需继续理解它；此时保留正确结果，后续学习继续围绕该部分展开。无需为了学习而重复改动正常代码，也无需给每个低风险文案变更新增测试。

掌握情况可通过延后复述或换输入再次检查。上述循环是针对当前目标提出的试行方法，不能承诺固定的学习提速或面试收益。

## 5. 第一轮建议：理解空证据分支

第一轮先研究“同步问答在最终检索结果为空时怎样返回”，不新增能力。

阅读入口：

- [QAController.java](../../rag-admin/src/main/java/com/enterprise/rag/admin/controller/QAController.java)：查找同步 `ask`，观察请求如何转换并交给服务层。
- [RAGServiceImpl.java](../../rag-core/src/main/java/com/enterprise/rag/core/rag/service/RAGServiceImpl.java)：查找同步 `ask` 中检索、相关回退及 `contexts.isEmpty()` 分支，再观察生成步骤的位置。
- [RAGServiceImplTest.java](../../rag-core/src/test/java/com/enterprise/rag/core/rag/RAGServiceImplTest.java)：阅读测试如何控制检索结果、缓存和生成器行为。

本次讨论时已只读核对：同步路径在检索及相关回退后仍没有上下文时，会在生成步骤前返回无结果响应。学习实验应明确缓存与路由条件，避免把某个分支的结论推广到所有配置。

建议验收：

1. 用户能画出这一小段调用链，解释请求对象与检索结果的作用。
2. 用户先预测空结果下是否调用生成器，再通过已有测试或适当的合成实验核对。
3. 用户亲自操作一个输入或断言，并解释结果。
4. 用户能讨论拒答的收益和代价，以及“检索到内容但内容无关”为什么是另一个问题。

这轮可以先采用本地合成测试，避免依赖 NIM 的在线稳定性。合成测试只证明被测控制流程，不能证明真实检索效果或回答质量。本文落盘不表示该学习任务已执行或验收。

## 6. 将学习成果转化为面试证据

每个准备重点讲述的能力，围绕下列问题积累少量真实材料。执行结果链接已有日志或验收记录，设计取舍链接对应设计，不把相同事实重复维护成多份报告。

| 深挖问题 | 应当能够说明的内容 |
| --- | --- |
| 为什么需要它？ | 具体场景、输入、原有问题与预期结果。 |
| 为什么这样设计？ | 当前约束、真实备选方案、选择理由及代价。 |
| 代码怎样实现？ | 入口、关键方法、数据流和失败分支。 |
| 怎样证明有效？ | 实际测试或实验，以及它能够证明的范围。 |
| 出问题怎样查？ | 亲自观察过的失败和定位过程；未经历的情形标为推演。 |
| 条件变化怎么办？ | 哪个假设会失效，需要修改或重新验证什么。 |

历史上由 AI 主导、后来才理解的设计，要区分原有实现与自己后来验证、修改的部分。测试数量、生成代码量和文档篇幅都不能单独证明项目掌握程度。

## 7. 初步停止迭代的标准

用户已接受设置阶段性停止条件；下列清单用于后续具体化验收，不表示当前已经达标。

- [ ] 已选定一个有限场景，说明用户、资料范围、典型问题和范围外需求；缺少真实使用证据的地方有明确标记。
- [ ] 该场景的主要路径可以按说明复现，失败状态清楚；不存在已知且阻断展示主路径的严重缺陷。
- [ ] 能展示与声明范围相匹配的评测和失败分析，分别说明 retrieval、generation、citation、no-answer 与 judge 的证据状态。
- [ ] 用户能够解释核心调用链，完成一项小修改并验证，复现和定位一种失败，说明至少一项真实设计取舍。
- [ ] 启动、演示、能力边界和剩余问题的说明清楚；代码与证据足以支撑简历中的描述。

达到这些条件后，建议暂停功能扩张，继续必要修复、学习巩固和求职。高级 Agent 能力、生产规模化和完整 Judge 校准不自动成为阶段停止的前置条件；已有债务仍如实保留，不能据此宣称对应能力完成。

只有实际使用暴露出反复出现的问题、现有方法确实不足，并且能够提出有边界的验收方式时，再考虑启动下一项功能。

## 8. 可复用的学习协作提示词

```text
这轮采用以学习和项目掌握为目标的协作方式。
我以 Java 为主，目标是能解释、验证并修改这一小段功能。

先只读相关代码，定位当前行为、关键调用链和已有测试。
用具体输入输出说明问题，区分已确认事实与假设。

在学习环节：
1. 先让我预测一个关键分支的结果，再核对代码。
2. 有实质设计取舍时，说明真实备选方案和代价，
   让我先表达选择与理由；不要为了流程编造备选方案。
3. 实现时保持小范围，为我安排一个适合当前基础的实际操作。
4. 验收时展示证据，让我解释一个关键测试，并预测一个变化案例。
5. 最后让我独立复述，再根据我的回答追问。
   先给提示，不要立刻替我回答。

每轮只聚焦一个核心知识点。
常规机械操作按现有授权连续完成。
工程验收和我的掌握情况分别判断，遵守仓库现有规则。
```

## 9. 调研依据与后续调整

以下资料在 2026-10-23 的讨论中查阅。官方实践可以提供方法参考，但不能证明某种流程是全网使用最多或对所有人最高效。

| 资料 | 本路线吸收的部分 |
| --- | --- |
| [Claude Code：Best practices](https://code.claude.com/docs/en/best-practices) | 探索、规划与实现分开；提前提供可执行的验证条件；检查实际证据。 |
| [Cursor：Best practices for coding with agents](https://cursor.com/blog/agent-best-practices) | 计划可由人修改；用明确输入输出和测试约束实现；小任务简化流程。 |
| [Microsoft：Spec-Driven Development](https://developer.microsoft.com/blog/spec-driven-development-ai-native-engineering/) | 连接需求、约束、实现与验收，按任务规模控制流程成本。 |
| [OpenAI：Rethinking skills and prompts](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra) | 按需读取上下文，减少重复、过时或不适用的规则。 |

[Anthropic 的技能形成研究](https://www.anthropic.com/research/AI-assistance-coding-skills) 对 52 名开发者学习陌生 Python 库进行了随机实验：AI 组即时测验平均 50%，手写组 67%，完成时间差异未达统计显著。研究观察到主动理解与追问的交互方式和较好成绩相关，但该交互分析不能证明因果，短期测验也不能直接代表长期成长。因此，本路线把预测、操作与复述作为待试行的方法，而不承诺确定收益。

下一次迭代优先检查：一个核心任务是否过大、用户是否能解释结果、实际操作是否促进理解、流程是否引入无效等待，以及场景是否出现真实需求。先用一轮小任务获取反馈，再决定是否将有效做法纳入现行协作手册；不预先扩充一整套新治理体系。
