# 工作空间归属与可见范围：前端设计规划

> 核对日期：2026-10-27。后续状态：用户已授权按本规划正式实现，并确认此前轨迹已验收；契约和进度以 [workspace-context-visibility](../../openspec/changes/workspace-context-visibility/design.md) 及其任务/实施记录为准。
> 本文保留最初设计理由与候选方案；实施后的接口、测试及未验证边界只在对应 change 维护，不把示意稿当作真实隔离验收记录。

## 💡 30秒人话设计主旨

后端已经按租户限制数据访问，但前端没有清楚告诉用户自己属于哪个组织，“公开”也容易被理解成对所有人开放。我们在现有侧栏、知识库和个人资料中补上工作空间归属与可见范围，让用户在原来的问答流程里就能理解边界。第一阶段沿用一个账号归属一个租户的约定；租户管理、成员邀请和组织切换另行规划。

[打开独立交互示意稿](../../prototype/workspace-context-demo/index.html)。示意稿所有账号、组织和资料均为明确标注的设计样例，没有连接后端，也不证明租户隔离成立。

## 1. 用户需要解决什么问题

面向已经登录的知识库使用者，首要任务仍是选资料、提问题。工作空间信息为这个任务提供上下文，不增加一层必须经过的入口页。

| 用户疑问 | 设计如何回答 | 审阅时检查什么 |
| --- | --- | --- |
| 我现在属于哪个组织？ | 侧栏在品牌下方持续显示工作空间名称，个人资料显示完整名称。 | 无需打开设置也能找到组织；长名称能读取全文。 |
| “公开”会让别的公司看到吗？ | 所有知识库可见性标签统一为“组织内公开”或“非公开”，表单旁解释范围。 | 列表、详情、创建和编辑的说法一致。 |
| 非公开是否表示只有我能看？ | 说明创建者和已授权用户仍可能访问，最终由服务端校验。 | 不把非公开错误描述成“仅自己可见”。 |
| 资料空了，是加载失败还是确实没有？ | 分别设计加载、失败、没有可访问资料三种状态。 | 错误不伪装成空列表；没有资料不伪装成没有组织。 |

租户是技术上的隔离单位，本方案在用户界面里将它称为“工作空间”，并用“组织内”解释共享范围。部门不是天然的租户；同一个组织里的多个用户也不是多个租户。

## 3. 界面怎么安排

### 3.1 侧栏：把归属放在导航之前

保留现有品牌、300 px 展开侧栏、76 px 折叠侧栏、三个导航和最近问答区域。在品牌和“新问答”之间插入一个紧凑的工作空间区：

```text
RAG                         收起

当前工作空间
组织名称                    只读

新问答
知识库
历史记录
```

- 工作空间区使用普通文本和组织图标，不放下拉箭头、切换按钮或绿色“隔离已验证”徽章。
- 名称最多两行；宽度不足时省略，同时提供可聚焦的“查看归属”文字按钮，打开既有个人资料弹窗。按钮 accessible name 包含完整组织名，全文也在资料弹窗中展示，不能只依赖鼠标悬停。
- 折叠状态保留一个“查看工作空间归属”图标按钮，键盘和触屏都可打开个人资料。现有导航、账号菜单不改位。
- 768 px 及以下继续使用现有抽屉。打开个人资料前先关闭抽屉，沿用当前焦点和背景锁定流程，避免两个遮罩叠加。
- 账号资料和工作空间一起加载；加载时骨架保留占位，失败时显示“工作空间资料暂不可用”，不编造“默认组织”。

### 3.2 知识库：统一标签，把解释放在操作旁

| 当前值或位置 | 建议文案 | 对现有行为的影响 |
| --- | --- | --- |
| `isPublic=true` 的列表与详情标签 | 组织内公开 | 只改展示；仍按服务端授权读取。 |
| `isPublic=false` 的列表与详情标签 | 非公开 | 只改展示；不撤销已有知识库授权。 |
| 创建／编辑中的可见性控件 | 可见范围：非公开／组织内公开 | 沿用现有布尔字段、默认值与提交方式，不新增权限选项。 |
| 选择组织内公开时的说明 | 本工作空间内的用户可以读取，其他工作空间不可见。 | 说明已接受的租户内公开语义，不承诺其他人可编辑。 |
| 选择非公开时的说明 | 创建者及已获授权的本工作空间用户可以访问。 | 不显示虚构的成员名单；访问仍由服务端校验。 |
| 知识库列表页说明 | 这里只显示当前账号可以访问的知识库。 | 沿用接口返回结果，前端不下载所有租户数据再过滤。 |
| 没有可访问知识库 | 暂无可访问的知识库。 | 复用现有创建操作；不凭空增加“申请加入”或“联系管理员”流程。 |

聊天页不增加全局警告横幅。保留原知识库选择器与输入区，所属工作空间已在侧栏交代；来源面板继续只展示接口允许返回的资料。

### 3.3 个人资料：补充归属，不新开管理后台

复用现有“设置 → 个人资料”，在用户名和邮箱后增加“所属工作空间”只读行。名称允许换行，不显示内部 tenant code、数据库 ID、成员数量和未经接口提供的角色。

在归属行下方显示：“资料可见范围以当前工作空间及知识库授权为准。”不提供改名、退出组织、邀请或切换操作。邮箱、用户名沿用真实接口；缺值用“未提供”，不能从 Token 猜出组织名。

同时参考现有组件与已安装的 `landing-page-design`、`redesign-existing-projects` 的局部改进方法。沿用项目自己的视觉和依赖，不为了满足通用 Skill 换掉整套界面。

| 项目 | 本方案的选择 |
| --- | --- |

| 可访问性 | 普通文字对比度目标至少 4.5:1，焦点／主要控件边界目标 3:1；提供可见焦点，不能只用颜色区分状态。键盘、触屏和 200% 缩放均列入后续验收。 |

## 5. 数据接线候选方案

### 5.1 推荐一个只读的当前账号上下文接口

建议未来新增 `GET /api/session/context`，返回既有 `ApiResponse` 包装。下列形状是候选 DTO，并非已发布契约：

```typescript
interface SessionContext {
  userInfo: { id: number; username: string; email: string }
  workspace: { id: string; displayName: string }
}
```

- 服务端从认证 principal 取得 userId、tenantId，校验当前数据库用户与租户的有效状态及归属一致后查询名称。不能接受 tenant selector，也不返回全部租户列表。
- `workspace.id` 按字符串传输，仅供前端比较身份是否变化，不展示、不回传作为业务请求的访问依据；它不是授权凭证。
- `displayName` 来自 tenant 表。若仍是迁移默认名称，先展示真实值；更名属于独立数据维护，不在本轮伪造中文企业名。
- 本接口不产生模型、向量检索或付费外调，不写历史或业务数据。响应不进共享缓存，建议 `Cache-Control: no-store`；显示字段不写普通日志。
- 沿用既有认证成功/失败语义，不泄露其他组织是否存在；状态失效时不能回退固定 tenant。新接口的错误码与状态细节须在正式 OpenSpec 设计中确定。

### 5.2 为什么不只给登录响应加一个名称

只扩展登录响应虽然较少新增接口，但仍需解决刷新页面恢复、组织名称变更和旧缓存问题。独立上下文接口能同时恢复账号资料和工作空间，且不要求为读取资料主动换发 Token。

选择 `/api/session/context` 还有一个当前代码约束：现有请求客户端对 `/auth/` 开头的失败明确不做自动 refresh。如果把“当前资料”直接放在 `/auth/me`，还必须特别设计这个例外，否则过期 Token 会使资料加载与其他页面行为不一致。新路由复用已有 `/api` 代理和共享请求客户端，不再创建第二套刷新拦截器。

### 5.3 前端生命周期

1. AppShell 建立有效会话后按当前 `sessionRevision` 发起一次上下文读取，多个组件共用同一次请求。路由切换不重复读取，主动重试才再请求。
2. 页面刷新时先清空上下文并显示加载态。成功后同时更新当前账号显示资料和工作空间；不把上次账号归属写入 localStorage。
3. 请求完成前如果用户退出或换号，旧响应立即丢弃，不能覆盖新账号资料。退出时同步清理上下文，沿用已有 `sessionRevision` 取消／丢弃机制。
4. 成功换发 Token 后重新读取上下文，更新期间不继续显示未经本次会话确认的组织名。新上下文若与已确认的 userId 或 workspace.id 不同，第一阶段清理会话和受控业务视图并要求重新登录，不在原页面静默切换组织。
5. 首次出现不同身份也必须先完成业务状态清理，才允许挂载新的知识库、历史、聊天和任务视图；正式接入时检查组件本地状态和旧异步响应，不能只清理侧栏文字。
6. 上下文读取失败不自动重发 ask、上传、索引或删除。普通网络/5xx 仅显示归属不可用并提供重试，现有经授权的业务请求仍由后端判断；401 沿用共享 single-flight refresh，刷新失败则退出。

## 6. 状态和异常怎么展示

| 状态 | 用户看到什么 | 操作与限制 |
| --- | --- | --- |
| 正常 | 当前工作空间及名称；资料页完整归属。 | 可查看归属，不能切换。 |
| 加载中 | 与两行文本等高的骨架及“正在读取工作空间”。 | 不显示上次身份，不挤动主要导航。 |
| 资料暂时失败 | “工作空间资料暂不可用”与“重试”。 | 只重试上下文，不触发模型或写操作。 |
| 名称缺失／响应形状不完整 | 按资料不可用处理。 | 不回退“默认组织”或把 workspace.id 当名称。 |
| 会话失效 | 既有登录失效提示，清空归属后跳回登录。 | 不出现旧工作空间闪回。 |
| 身份发生变化 | 清理旧业务视图，提示“账号归属已变化，请重新登录”。 | 第一期不静默迁移当前聊天、任务或草稿。 |
| 工作空间存在但知识库为空 | 保留组织名，列表显示没有可访问资料。 | 不把“空资料库”当“没加入组织”。 |
| 超长名称 | 侧栏最多两行，个人资料完整换行。 | 键盘与触屏都能查看全文。 |
| 访问不可见资源 | 沿用“资源不存在”；同租户权限不足沿用既有无权访问语义。 | 不显示“这是 B 公司的资料”等泄漏存在性的解释。 |

## 7. 分阶段落地及验收

最初规划交付完成 S0。后续用户已授权正式接入，S1–S3 的实际进度见 [正式任务](../../openspec/changes/workspace-context-visibility/tasks.md)；下表保留阶段定义，不在本文重复记录测试计数。

| 阶段 | 交付物和顺序 | 达到什么才算完成 |
| --- | --- | --- |
| S0：审阅设计 | 本文与独立示意稿；先看正常、失败、长名称，再看窄屏及深色。 | 用户能确定位置、叫法、范围，示意稿不连接真实服务。 |
| S1：建立正式契约 | 在当前 active change 按规则收口或经授权挂起之后，为上下文能力创建独立 Type C change；补 proposal、design、tasks 和相关 spec delta。 | 事前闸门确认接口、失败行为、身份变化清理范围、实施授权和调用预算。 |
| S2：接入只读归属 | 先写上下文接口与身份测试，再接入共享状态、侧栏和个人资料，最后统一可见性文案。 | 聚焦 Java 测试、相关前端回归、包含 vue-tsc 的正式构建及 DocAndScope 通过；身份变化涉及业务视图时覆盖其清理。 |
| S3：完成体验与隔离演示 | 用受控合成 fixture 做双组织浏览器验证，另行授权后才访问真实业务环境。 | 区分浏览器体验证据、服务端隔离证据与真实业务证据，不把模拟切换当作租户切换实现。 |

后续正式验收至少覆盖以下场景，测试结果只记录在对应 change 的验收记录：

- 登录、刷新页面、Token 轮换之后均能得到正确归属；失败/空名/超长名有明确显示。
- A 账号的慢响应不能在退出或 B 账号登录后覆盖归属、知识库、历史、聊天、来源、上传任务和执行轨迹。
- 同一租户下两个账号不被误判成跨租户验证；受控 fixture 中 A/B 直接猜对方资源 ID 时仍走服务端隔离。
- 深浅主题，320/390/768/1440 px 宽度，短窗口、长名称和 200% 缩放；抽屉与资料弹窗的 Esc、焦点返回、键盘循环及触屏入口可用。
- 可见性措辞与现有 `isPublic`、创建者和 KB permission 的读取/写入权限保持一致，不能因为文案改成“组织内公开”就扩大写权限。
- 不发送客户端指定租户的请求；上下文请求和普通重试不触发 ask、embedding、rerank、judge 或上传。

试用有帮助，主要贡献是把设计从“加一个组织标签”推进到“位置、文案、状态、恢复流程和验收”完整闭环。它不能决定租户权限和接口契约，这些仍以当前代码和 OpenSpec 为依据；本次未做用户研究，不能宣称可用性或效率已经提升。

## 决策记录

### D1：先展示归属，沿用现有三个主入口

- **当时面临哪几个选择？** 可以新增整套租户后台，也可以先在日常问答路径中补充归属和可见性。
- **最终选了谁及理由？** 选择后者。当前用户最缺的是知道自己在哪里、公开意味着什么，现有产品还没有成员关系和组织切换契约。
- **其他方案的代价是什么？** 完整后台需要租户生命周期、成员管理、权限与审计等独立能力；只画入口会让用户误以为已经能操作。以后真有多组织管理需求时再规划。

### D2：用独立只读接口恢复上下文

- **当时面临哪几个选择？** 可以扩展登录/刷新响应、读取 JWT 当作展示资料，也可以增加当前会话上下文接口。
- **最终选了谁及理由？** 推荐第三种。它能恢复刷新页面后丢失的用户资料，并从数据库返回当前组织名称；选择 `/api` 路由可复用现有 Token 刷新行为。
- **其他方案的代价是什么？** 扩展登录响应仍需额外设计恢复/更新流程；JWT 无组织名称且展示资料可能陈旧；新接口的代价是每次会话建立及 Token 轮换增加一次本地服务读取，并要处理竞态与失败态。

### D3：身份变化先重新登录，不在旧页面静默换组织

- **当时面临哪几个选择？** 可以在 Token 刷新后直接替换组织标签，也可以先隔离并清理旧会话视图，再要求重新登录。
- **最终选了谁及理由？** 选择后者。当前没有用户主动切换组织的产品契约，旧聊天、上传或缓存不能因为标签变了就自动归入新组织。
- **其他方案的代价是什么？** 自动切换的体验更连贯，但需要逐一证明业务状态生命周期与清理完整性；重新登录会中断当前工作，正式设计必须明确提示和清理，不声称替用户迁移草稿。

### D4：复用现有视觉，按项目事实取舍外部 Skill

沿用当前字体、颜色、Lucide、侧栏和弹窗结构，让新增归属自然进入现有工作台。外部 Skill 的完整状态与局部设计方法适用；营销结构和展示动画不适用。租户 CRUD、邀请、切换、配额、计费和新角色均保持在本轮范围之外。
