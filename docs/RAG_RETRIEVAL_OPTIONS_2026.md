# RAG 检索架构优化：候选方案与决策对比

> **文档版本**：2026-09-28
> **用途**：作为检索架构优化讨论的输入文档。本文档**自包含**，读者无需了解成文过程。
> **给接手 agent 的说明**：本文档给出的是**通用证据与候选方案**，不含对具体代码库的假设。请先执行 §8「本地待确认问题」，把本文档的方案映射到本地项目实际代码上，再产出优化方案。**不要跳过 §7 的评测协议直接改代码** —— §6 说明了一个会让架构决策系统性偏航的陷阱。

---

## 1. 结论摘要

1. **混合检索（dense + 稀疏）没有被替代**，2026 年它仍是推荐的生产基线。不要以"架构过时"为由替换它。
2. **但 RRF 融合函数有充分证据表明应被取代**：凸组合（convex combination / 加权和）在域内与域外均优于 RRF。这是投入最小、证据最硬的一步。
3. **cross-encoder 重排是单项收益最大的改造**，且不增加存储。
4. **索引期 chunk 富化**（每 chunk 预生成假设问题 / 上下文摘要）是性价比最高的一步：一次性成本，在线零开销。
5. **不建议做的**：用 Agentic RAG 或 GraphRAG 取代混合检索。前者贵 3.6× 且重排能力不如显式重排；后者的收益大多能用"把 1-hop 关系直接塞进 chunk"这种便宜做法拿到，纯图检索效果很差。
6. **决策前提**：必须先建立**端到端生成质量**评测。只按检索指标（recall/nDCG）做架构决策会系统性高估高级检索的收益（见 §6）。

## 3. 候选方案对比

每个方案给出：**是什么 / 证据 / 预期收益 / 成本 / 风险 / 前置条件**。

### 方案 A：RRF → 凸组合加权（Convex Combination）

- **是什么**：把 `score = Σ 1/(k + rank_i)` 换成 `score = α·dense + (1-α)·sparse`（分数需先归一化）。
- **证据**：[E1] CC(α=0.5) 0.726 > RRF(k=10) 0.716 > RRF(k=60) 0.695；[E2] 论证 CC 优于 RRF 且调参样本效率高；[E3] 20/20 单元胜过等权 RRF。
- **预期收益**：中等。属"免费"提升 —— 改动小、无新增依赖、无延迟增加。
- **成本**：低。需要一次 α 扫描（在自有验证集上）。
- **风险**：
  - **α 是数据集特定的，必须本地调优，不可沿用他处数值** [E3]
  - 分数归一化策略会引入选择：min-max / z-score / 分位。若两路分数尺度差异大且不做归一化，CC 比 RRF 更脆弱 —— 这是 RRF 支持者的核心论点，需在本地验证
  - 若当前是**多路**（>2）融合，CC 的参数空间比 RRF 大
- **前置条件**：有可复现的评测集（见 §7）
- **优先级**：**最高**

### 方案 B：cross-encoder 重排 + 候选深度调优

- **是什么**：检索出 N 个候选（N 远大于最终 k），用 cross-encoder 对 (query, doc) 联合打分后取 top-k。
- **证据**：[E1] 全实验单项最大增益（MRR@3 +17.2pp / Recall@5 +12.1pp）；[E9] Multigrid 称其为"当今每单位工程投入质量最高的做法，且不增加存储"。
- **预期收益**：高。
- **成本**：中。每 query 一次模型调用（可用 API 或本地部署）；延迟显著增加。
- **风险**：
  - **跨域重排器可能有害**：[E3] 用 off-the-shelf MS MARCO cross-encoder 接在融合结果上，nDCG 从 0.753 掉到 0.694。**必须用目标域验证**
  - 候选深度是重要超参，[E1] 专门做了消融；太浅则重排无意义，太深则延迟爆炸
  - 重排后与词法信号的融合权重需要重新校准
- **前置条件**：延迟预算允许；有目标域标注或可构造的验证集
- **优先级**：**高**（若尚未具备）

### 方案 C：索引期 chunk 富化（假设问题 / 上下文摘要）

- **是什么**：建索引时用 LLM 为每个 chunk 生成
  (a) 若干**假设问题**（HyPE 式），嵌入后让检索变成 question→question matching；
  (b) 或一段**上下文摘要**前置到 chunk 文本（Contextual Retrieval 式）。
- **证据**：[E7] context precision 最多 +42pp、claim recall 最多 +45pp，平均 +20pp / +16pp；每 chunk 一次 LLM 调用，**在线零额外成本**；与重排/multi-vector/query decomposition 兼容。[E1] 中 contextual retrieval 也显示 consistent gains。
- **预期收益**：高（在"查询与文档语体不匹配"的场景收益尤其大）。
- **成本**：中高，但**一次性**。与语料规模成正比。
- **风险**：
  - 索引期成本高，大语料需要评估
  - 会放大索引体积（假设问题需额外存储嵌入）
  - LLM 生成质量直接影响效果；需抽检
- **前置条件**：离线 LLM 预算；索引可重建
- **优先级**：**高**（注意：部分项目可能已实现此机制，先确认再投入）

### 方案 D：稀疏腿升级（学习稀疏 / SPLADE / BM42）

- **是什么**：把 BM25 换成学习稀疏检索器。
- **证据**：[E1] 引述 SPLADE 及 decoder-only LLM 骨干可提升稀疏检索质量；[E3] 用 BM42 作为稀疏腿（但其单独 nDCG@10 仅 0.612，明显弱于 BM25 类基线，导致等权 RRF 严重低估它）。
- **预期收益**：中。
- **成本**：中高（需训练或引入模型、索引结构变化）。
- **风险**：学习稀疏的单路强度可能**弱于**调好的 BM25 [E3]，替换后需要重新平衡 α。
- **优先级**：低-中（先做 A/B/C）

### 方案 E：Late interaction（ColBERT 式多向量）

- **是什么**：每个 token 一个向量，用 MaxSim 打分。
- **证据**：[E9] HF sentence-transformers v6.0 已原生支持；是视觉文档检索 SOTA。[E9-Multigrid] 给出明确决策顺序：**先 hybrid → 再 cross-encoder 重排（零存储成本）→ 仅在"重排延迟是瓶颈"或"查询真正多面向且长"时才用 late interaction → 动手前先按语料规模算存储账**。压缩后索引约为单向量全精度索引的 2×，相比二值量化稠密索引（19GB）大近两个数量级。Qdrant 官方建议只用于对数百候选重排。
- **预期收益**：高（多面向长查询、视觉文档），但对多数场景**不优于方案 A+B 的组合**。
- **成本**：**很高**（存储与 serving）。
- **优先级**：**低**（除非瓶颈明确是重排延迟）

### 方案 F：GraphRAG

- **是什么**：构建实体-关系图，检索连接子图。
- **证据**：[E6] 在 STaRK-Prime 上的 9 场景对比（Claude 3.7 Sonnet）：

  | 场景 | Hit@1 | MRR |
  |---|---|---|
  | S2：文档里直接塞 1-hop 关系（**不做图搜索**） | **0.6972** | **0.7531** |
  | S5：向量检索 + 预定义 KG | 0.6422 | 0.7011 |
  | S3：纯 KG 检索 | 0.1376 | 0.1542 |
  | S8：Agent + 文档检索器 | 0.6881 | 0.7549 |
  | S9：Agent + 文档检索器 + **KG 工具** | 0.6055 | 0.6834 |

  [E4] 另证：GraphRAG 撞构建墙，可扩展变体在各共享档位上仍不如 BM25。
- **预期收益**：**低**（除非有预定义的、高质量的领域 KG）。
- **成本**：**极高**（[E4] 每 corpus token 最多 24.6 个生成 token；[E8] 图构建约 37B 输入 + 18B 输出 token）。
- **决策建议**：
  - 有高质量预定义 KG → 可考虑 S5 式结合
  - **没有预定义 KG → 先试 S2 式（把 1-hop 关系直接塞进 chunk）**，它打败了正牌 GraphRAG，成本只是前者零头
  - **不要**给已有 agent 加 KG 工具（S9 比 S8 更差）
- **优先级**：**低**

### 方案 G：Agentic RAG

- **是什么**：LLM 编排检索循环，自主决定工具、次数、是否继续。
- **证据**：[E5] 无普适赢家；重排不如 Enhanced；贵 3.6×；建议混合。 [E4] 大规模语料上 BM25 处 Pareto 前沿，**agentic 推理应放在全局候选发现之后**；把检索原语换成 BM25 后 agent 得分 36.9 → 69.4，token 降至 1/9。[E8] 若 agent 能力足够强，"重脑+精确手"（LLM 出结构化查询 + 轻量倒排索引）可以匹配重型混合检索，构建成本低 41×。
- **预期收益**：中（多跳、需要覆盖检查的复杂查询）；单跳事实型查询收益为负（成本）。
- **成本**：高（3.6× 起，见 [E5]）。
- **风险**：agent 一旦选定文档就不易重新考虑（[E5]：重复检索时 53% 文档不变）；宽泛/噪声域下路由可靠性下降。
- **优先级**：中-低（**作为补足层，不作为替代层**）

### 方案 H：自适应路由

- **是什么**：按 query 复杂度分流（简单查询跳过重链路，复杂查询走完整链路 / 多跳）。
- **证据**：间接支持来自 [E1]（HyDE/多查询等查询扩展对精确数值查询收益有限）、[E5]（自适应改写最有效）。
- **预期收益**：中（主要收益在**成本与延迟**，而非质量）。
- **成本**：中（需训练/维护分类器）。
- **优先级**：中（在所有质量手段做完后，作为成本优化）

### 方案 0：保持现状

- 若 §7 的评测显示当前 recall 与生成质量已满足业务要求，则**本方案完全合理**。本档列在最后不是因为它差，而是因为它常被跳过。

## 4. 决策矩阵

按「证据强度 × 收益 / 成本」排序：

| 排序 | 方案 | 证据强度 | 预期收益 | 成本 | 风险 | 建议 |
|---|---|---|---|---|---|---|
| 1 | **A. RRF → 凸组合** | 强（3 篇独立） | 中 | 低 | 低 | **立即做** |
| 2 | **B. cross-encoder 重排** | 强 | 高 | 中 | 中（跨域模型有害） | **立即评估** |
| 3 | **C. 索引期富化** | 强 | 高 | 中高（一次性） | 中 | **优先排期** |
| 4 | H. 自适应路由 | 中 | 中（成本侧） | 中 | 低 | 后续 |
| 5 | G. Agentic RAG | 中（结论是"不普适"） | 中 | 高 | 中 | 仅作补足层 |
| 6 | D. 学习稀疏 | 中 | 中 | 中高 | 中 | 暂缓 |
| 7 | F. GraphRAG | 强（结论是"多数不划算"） | 低 | 极高 | 高 | 仅试 S2 廉价版 |
| 8 | E. Late interaction | 中 | 高（特定场景） | 很高 | 高 | 除非延迟是瓶颈 |

**推荐目标架构**：

```
查询
 └─ 路由层（自适应：简单查询直接答 / 复杂查询走完整链路）
     ├─ 查询改写（按需；不要无脑 HyDE —— 对精确数值查询收益有限 [E1]）
     ├─ 混合检索：dense + 稀疏（BM25 或学得稀疏）
     │   └─ 融合：凸组合加权（不是 RRF），α 按域调优
     ├─ cross-encoder 重排（候选深度要够；注意跨域模型可能有害 [E3]）
     └─ 索引期富化：每 chunk 的假设问题 / 上下文摘要（在线零成本 [E7]）
 └─ 按需 Agentic 循环 —— 仅在全局候选发现之后，用于多跳与覆盖检查 [E4]
```

核心判断：**不是"用新架构取代混合检索"，而是"混合检索保底 + 融合函数升级 + 重排 + 索引期富化 + 可控的 agentic 补足"。**

## 6. 关键陷阱（决策前必读）

1. **retrieval-generation gap** [E6]：检索指标提升不带来成比例的生成质量提升（R@20 0.7154 → 0.6119）。**只按检索指标做架构决策会系统性高估高级检索的收益。** 必须用端到端指标决策。
2. **融合系数不可移植** [E3]：α / λ / κ 全部是数据集特定的。照抄他处数值是常见错误。
3. **跨域重排器可能有害** [E3]：off-the-shelf MS MARCO cross-encoder 使 nDCG 0.753 → 0.694。
4. **agentic 不等于更强** [E5]：贵 3.6×，且重排能力不如显式重排。agent 一旦选定文档不易反悔。
5. **"高级"不必然是"更优"** [E4]：大规模语料上朴素 BM25 处 Pareto 前沿。架构复杂度必须由业务需求证明，而非由新颖性证明。
6. **纯图检索是灾难** [E6]：S3 Hit@1 仅 0.1376。图信息要**融进文本**才有用。

## 7. 评测协议（强烈建议先建立）

在改任何代码之前：

1. **构建查询集**：覆盖 (a) 简单事实型、(b) 精确匹配/数值型、(c) 多跳/多面向、(d) 应拒答型。规模不必大，但每类都要有。
2. **标注**：gold chunk / gold answer。
3. **双轨指标**：
   - 检索侧：Recall@k、nDCG@10、MRR
   - **生成侧：answer accuracy、faithfulness、context precision/recall**（用 LLM-as-judge 或人工抽检）
4. **成本指标**：每 query 的 token 数、延迟 P50/P95、索引构建成本。
5. **决策规则**：只有当**生成侧指标**显著提升，且成本增量可接受时，才采纳一个方案。

> [E1] 的教训：query expansion（HyDE、multi-query）和 adaptive retrieval 在精确数值查询上收益有限；CRAG 0.658 打不过简单混合融合 0.695。**很多"高级"组件在受控实验中并不奏效。**

## 8. 本地待确认问题（交给接手 agent）

请先回答以下问题，再产出优化方案：

1. **当前架构**：检索链路包含哪些阶段？dense 用什么模型、稀疏用什么、融合用 RRF 还是加权和？
2. **是否已有 cross-encoder 重排**？若有，候选深度是多少？重排分数如何与检索分数结合？
3. **是否已有索引期富化**（每 chunk 的假设问题 / 关键词 / 上下文摘要）？若已实现，注意方案 C 的边际收益会大幅缩小。
4. **是否有多路融合**（>2 路，如额外的手工特征 / 图谱 / tag）？若有多路，方案 A 的参数空间评估方式需调整。
5. **是否已有端到端评测**？若只有检索指标，先补 §7。
6. **语料规模与增长预期**？这直接决定方案 D/E/F 是否可行（[E4] 的规模效应）。
7. **延迟与成本预算**？重排与 agentic 都是延迟敏感项。
8. **查询分布**：单跳事实型为主，还是多跳/多面向为主？这决定方案 G/H 的价值。
9. **是否已有关联数据（KG / 结构化表 / 关系）**？若没有预定义 KG，方案 F 只考虑 S2 廉价版。
10. **索引可否重建**？方案 C 需要重建索引。

**特别提示**：若本地项目是 **RAGFlow**，其主检索链路已使用加权和而非 RRF，且已实现索引期关键词/问题富化 —— 即方案 A 与方案 C 已部分具备。此时优先级应调整为 **方案 B（重排候选深度）** 与 **§7 评测体系**。相关代码位置：`rag/nlp/search.py`（`build_fusion_expr`、`retrieval`、`rerank_by_model`）、`rag/svr/task_executor.py`（`auto_keywords` / `auto_questions`）、`rag/advanced_rag/knowlege_compile/raptor.py`（RAPTOR 摘要作为普通 chunk 入库，查询期无特殊处理）。
