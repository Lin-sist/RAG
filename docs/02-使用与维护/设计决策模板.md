# design.md 规范：人话设计主旨与决策记录（Decision Record v2.1）

> 整理日期：2026-10-27。状态：维护说明；目录整理不等于重新完成运行或真实业务验证。

> **核心目的**：让项目主人不用啃源码，也能理解关键方案为什么这样选、有什么代价；按 [`AGENTS.md`](../../AGENTS.md) 第 10 节执行。
> **写作底线**：使用完整句子讲清因果，不能只堆变量名；比喻按需使用，不靠增加篇幅证明严谨。

---

## 一、`design.md` 顶部必写：`## 💡 30秒人话设计主旨`

先用一小段通俗中文说明以下内容，再列必要参数；不固定句数：
1. **现在缺什么 / 痛点是什么？**
2. **核心方案是什么，改完会有什么直观变化？**
3. **这次刻意不碰什么？**

---

## 二、`design.md` 末尾必写：`## 决策记录`（按影响选择详略）

重点记录影响接口、数据、成本、失败行为或难以撤销的真实取舍，以及关键范围边界。普通实现选择不用逐项展开；没有实质取舍时说明沿用什么既有约定，不编造备选方案。

重要决策用以下三问，简单选择一句理由即可。例如：“沿用现有主题 store，避免登录页和主页面分别保存主题后出现不同步。”

```markdown
### D1：<用一句人话概括这个决策点，例如“AI 阅卷中途断网时怎么算分”>
- **当时面临哪几个选择**：说明真实候选方案各自怎么做。
- **最终选了谁 + 理由**：讲清直观因果和必要的工程理由；比喻可选。
- **其他方案的代价**：说明在本项目约束下的风险或成本，不把未选方案一概写成错误做法。
```

## 四、硬性自检清单

1. **真实性**：只写真实取舍；普通实现选择由 Agent 在批准范围内判断。涉及范围、风险或授权变化时才交用户确认。
2. **可读性**：用户不看代码也能理解选择与理由；不删主谓宾，也不为比喻和三问格式凑篇幅。
3. **适度记录**：重要决策能解释替代方案的代价，简单选择一句理由足够；不把执行进度和测试计数复制进设计。
